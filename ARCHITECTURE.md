# Architecture

Runtime surfaces, directory boundaries and dependency direction for Chartiko (repository directory ChartScreenPlus).

## Product Identity And Hosting

- Public product: **Chartiko**, at `https://www.chartiko.com` (VPS, reported by owner).
- Header and favicon share `frontend/public/favicon.svg`: a C/chart mark with the existing ink/yellow palette. Public metadata and chrome use Chartiko.
- EOD/end-of-day labels appear only within Admin. Charts retain session dates and closing prices; ingestion and data contracts remain EOD-only.
- `/var/www/alphapulse`, `alphapulse-*` units and the health service identifier remain infrastructure compatibility names. Renaming requires a coordinated VPS migration.

## Runtime Surfaces

- **Laravel (repository root)** — API, auth and admin. PHP 8.4 / Laravel 13. Owns the database, the framework migrations and Laravel's own Vite assets under `resources/`.
- **React SPA (`frontend/`)** — the trader surface (Screener, Chart, Portal). React 19 + Vite + Tailwind 4 with its own toolchain and dev server.
- **Python engine (`engine/`)** — FastAPI HTTP service that owns scraping, indicators and deterministic signals. Python 3.10 with its own venv and requirements files; exposes `/health`, `GET /eod/{symbol}` (fetch + parse only), `POST /indicators/compute` (pure indicator math), `POST /signals/detect` (deterministic signal rules), `POST /patterns/detect` (deterministic chartist pattern rules) and, for calibration only, `POST /patterns/near-misses` and `GET /patterns/parameters`. It has no database access.

## Directory Boundaries

- `frontend/` is a standalone npm project: its own `package.json`, `vite.config.ts`, `tsconfig*.json` and lockfile. It MUST NOT be wired into Laravel's root Vite pipeline.
- Laravel's root `package.json`, `vite.config.js` and `resources/` belong to Laravel assets only.
- `engine/` is a standalone Python project: its own `.venv`, `requirements*.txt` and `pyproject.toml`. It MUST NOT be entangled with Laravel's PHP code.
- `alphapulse/` is a design/intent reference prototype; it is not a product runtime surface.

## SPA Routing And Shell

- The SPA uses **react-router** (`createBrowserRouter` + `RouterProvider`) as a client-side data router; the shell is a layout route (`frontend/src/layouts/AppLayout.tsx`) that renders `AppHeader` plus an `<Outlet />`.
- Route list:
  - `/` -> public Screener (filter controls + Candidate list; anonymous) with search metadata
  - `/screener` -> legacy client redirect to `/`, preserving query and hash
  - `/como-funciona` -> public user manual (`HowItWorksPage`): getting started, data, candidate list, every filter, indicator, signal and chart pattern, the chart and the account; texts in the typed `frontend/src/i18n/guide/{es,en}.ts` catalogs, kept in step with the UI labels by `HowItWorksPage.test.tsx`
  - `/chart` -> legacy direct link to the "no ticker selected" guidance (anonymous, no request); it is not a navigation tab
  - `/instruments/:ticker` -> instrument chart for one ticker (anonymous deep link)
  - `/admin` -> Admin ingestion panel (admin-only; guest/non-admin see a restricted state)
  - `/portal` -> Portal (the signed-in user's owned Saved Screeners and Watchlist entries plus their Alert controls; a Visitor is redirected to `/login`)
  - `/portal/notificaciones` -> notification inbox (`NotificationsPage`, `NOTIFICATIONS_ROUTE`; `RequireAuth`, noindex; the Portal tab stays active on it)
  - `/login` -> sign-in screen
  - `/register` -> account-creation screen
  - `*` -> token-styled Not Found placeholder (rendered inside the shell)
- Tab paths and label catalog keys are single-sourced in `frontend/src/nav.ts` (`NAV_ITEMS`, `DEFAULT_ROUTE`). The tabs are Screener, Cómo funciona, Admin (for Admin users) and Portal; charts are reached through Candidate and Watchlist ticker links. Auth paths are exported there too (`LOGIN_ROUTE`, `REGISTER_ROUTE`) and the router derives child segments from them with `routeSegment`.
- The header (brand, `ES | EN` language selector, user pill) lives in `frontend/src/components/AppHeader.tsx`; it is auth-aware and shows the signed-in user plus a sign-out control, or a translated sign-in link for a Visitor. For a signed-in user only, an icon-only `NotificationBell` links to `/portal/notificaciones`; its accessible name carries the exact unread count ("Notificaciones, N sin leer") and the visual badge is capped at "9+". Visitors get no bell and no notification request. Data refresh remains an action in Admin, with no disabled header button.
- History routing needs a server-side SPA fallback when the SPA is deployed behind Laravel or another host; the Vite dev server already provides it. Configuration is deferred to deployment work.

## Localization (Spanish / English)

- SPA: `frontend/src/i18n/` owns the locale registry (`locales.ts`), typed catalogs (`messages/es.ts` defines the shape, `messages/en.ts` must match it), `translate.ts`, `Intl` formatters (`format.ts`) and `I18nProvider` (above `AuthProvider` and the router). `useI18n()` returns `t` and locale-bound formatters; `LanguageSelector` in the header switches language in place without navigation.
- Resolution: saved device choice (`localStorage` `chartiko.locale`) -> first supported browser language by primary subtag -> Spanish. The provider sets `<html lang>`; `RouteMetadata` translates titles/descriptions while robots/canonical rules stay language-independent. The static `index.html` remains Spanish (no translated URLs or hreflang).
- Color theme (`ui-dark-mode`): `data-theme` on `<html>` selects light or dark values of the same `index.css` tokens. Resolution: saved choice (`localStorage` `chartiko.theme`) -> `prefers-color-scheme` (followed live until the user chooses). An inline script in `index.html` applies it before the first paint; `ThemeProvider` (above `I18nProvider`) owns it afterwards.
- API: `lib/api.ts` sends `Accept-Language` with the selected locale; `App\Http\Middleware\SetLocale` (prepended to the `api` group, configured by `config/locales.php`) sets the app locale (fallback `es`) and `Content-Language`. Messages live in `lang/{es,en}/` (`validation`, `auth`, `passwords`, `pagination`, `messages`). Status codes, JSON shapes, `errors` keys and Signal codes never depend on the language.
- Adding a language: `docs/specs/app-multilanguage.md` -> "Adding A Language".

## Authentication (First-Party SPA)

- The SPA authenticates with **Laravel Sanctum first-party SPA auth**: an HTTP-only session cookie plus CSRF. **No API tokens / Bearer auth** are issued or used for the SPA. `laravel/sanctum` v4 is installed, `config/sanctum.php` is published, and `bootstrap/app.php` calls `$middleware->statefulApi()`.
- Endpoints (`routes/api.php`, `app/Http/Controllers/Auth/AuthController.php`):
  - `POST /api/register` -> 201 + `{ user }`, creates the account and starts the session.
  - `POST /api/login` -> 200 + `{ user }` (throttled `6,1`); invalid credentials -> 422.
  - `POST /api/logout` (`auth:sanctum`) -> 204, invalidates the session.
  - `GET /api/user` (`auth:sanctum`) -> 200 + `{ user }`, or 401 for a guest.
  - `GET /sanctum/csrf-cookie` (registered by Sanctum) seeds the `XSRF-TOKEN` cookie.
- Login uses `Auth::attempt` on the `web` guard; password hashing comes from the `User` model's `hashed` cast; `#[Hidden]` keeps `password`/`remember_token` out of responses.
- The SPA client is `frontend/src/lib/api.ts` (fetch, `credentials: 'include'`, `X-XSRF-TOKEN` echoed from the `XSRF-TOKEN` cookie, `/sanctum/csrf-cookie` before mutations). Auth state is `frontend/src/auth/` (`AuthContext.tsx` provider, `context.ts`, `useAuth`), bootstrapped from `GET /api/user`.
- **Dev same-origin model:** the Vite dev server proxies `/api` and `/sanctum` to `http://127.0.0.1:8000`, so the browser is same-origin and cookies/CSRF work without CORS. `SANCTUM_STATEFUL_DOMAINS` lists `localhost`, `127.0.0.1`, `localhost:5173` and `127.0.0.1:5173`. Production is expected to serve the SPA and API from the same origin.

## Account Self-Service

- `AccountController` (`auth:sanctum`, session-only like `AuthController`, never a `user_id`): `PATCH /api/account {name}` -> `{user}` (`throttle:30,1,account-profile`); `PUT /api/account/password {current_password, password, password_confirmation}` -> 204, deletes the user's other `sessions` rows and regenerates the current id (`throttle:6,1,account-password`); `GET /api/account/export` -> JSON attachment `chartiko-account-<date>.json` (`throttle:5,1,account-export`); `DELETE /api/account {password, confirmation}` (`DELETE` or `ELIMINAR`) -> 204 (`throttle:6,1,account-delete`). Admins get `422 account.admin_cannot_delete`.
- `App\Services\Account\AccountExporter` builds `chartiko-account-export-v1` from the User's relations (profile, watchlist, saved screeners, alerts, notifications, own `login_events`, own session metadata, AI card requests); no password hash, remember token, session ids or payloads.
- `App\Services\Account\AccountDeleter`, one transaction: `login_events` row `account_deleted` (email only, no user id/IP/agent) -> delete the user's `sessions` (no FK) and any tokens/reset rows -> `$user->delete()` (notifications via the `deleting` hook; watchlist, screeners and alerts cascade; `login_events`/`ai_company_card_generations` user ids become null). The controller then logs out with `logoutCurrentDevice()`, forgets the cached Sanctum user and invalidates the session.
- SPA: `/portal/cuenta` (`ACCOUNT_ROUTE`, `pages/AccountPage.tsx`), linked from the header name chip and the Portal; `accountApi` in `lib/api.ts`; `setCurrentUser` on the auth context updates the name or clears the user after deletion (the guards then go home). Spec: `docs/specs/account-self-service.md`.

## Authorization And Admin Boundary

- Accounts carry a single `role` string on `users.role`, defaulting to `user`. Two roles exist: `User::ROLE_USER` (`user`) and `User::ROLE_ADMIN` (`admin`); `User::isAdmin()` is the only check callers need. Multi-role/RBAC, teams and ownership are out of scope.
- The role is **not** mass-assignable (`role` is deliberately absent from `User`'s `#[Fillable]`), so it can never be set through registration or any request payload. The DB/model default keeps new accounts at `user`.
- Admin is enforced **server-side** by `App\Http\Middleware\EnsureUserIsAdmin` (alias `admin`, registered in `bootstrap/app.php`): the authenticated user must exist and be an admin, otherwise `abort(403)`.
- Admin-only routes live in a dedicated group in `routes/api.php`: `Route::middleware(['auth:sanctum', 'admin'])->prefix('admin')`. Ordering matches the status contract — guests fail `auth:sanctum` with **401**, authenticated non-admins fail `admin` with **403**, admins pass.
- `GET /api/admin/ping` is a guard probe (`{ok:true}`), not product behavior. The admin ingestion endpoints (`admin-ingestion-panel`) extend this same group, so every admin surface shares one 401/403 boundary.
- Admin is granted **out of band only** via `php artisan app:make-admin {email}` (promotes an existing account, fails if the email is unknown) or `UserFactory::admin()` in tests. There is no HTTP path to grant admin.

## Ingestion Path (EOD)

- **Sources:** Yahoo Finance's chart response (`range=2y`, daily OHLCV) is queried first and translates class-share tickers such as `BRK.B` to `BRK-B`. Stooq daily EOD CSV remains the fallback (`https://stooq.com/q/d/l/?s={symbol}.us&i=d`, columns `Date,Open,High,Low,Close,Volume`) because its anti-bot challenge can consume the full request timeout before returning unusable content. Both upstreams are unofficial integrations whose terms, availability and rate limits remain operational risks.
- **Chinese wall — engine fetches/parses, Laravel persists.** The engine does **not** touch the database. `engine/app/sources/stooq.py` exposes pure Stooq CSV and Yahoo chart parsers plus `fetch_eod(symbol)` (httpx); the `Bar` pydantic model lives in `engine/app/models.py`. `GET /eod/{symbol}` returns `{symbol, bars: [{date, open, high, low, close, volume}]}`; empty/unknown data is `404` and an upstream failure/unusable payload is `502` (controlled JSON `{detail}`).
- **Laravel persistence.** `App\Services\Engine\EngineClient::eodBars($ticker)` calls `Http::get(config('engine.url').'/eod/'.$ticker)->throw()`. The artisan command `ingestion:scrape {ticker}` resolves the `Instrument` by ticker, fetches the bars, and upserts them into `daily_bars` by the unique `(instrument_id, date)` key inside a transaction; it writes nothing when the engine fails. Re-running is idempotent.
- Tests never use the network: the engine parser runs against the committed fixture `engine/tests/fixtures/stooq_nvda.csv`, and Laravel uses `Http::fake`.

### Ingestion Runs (Orchestration Ledger)

- Laravel owns the run ledger: `ingestion_runs` (one row per run: `status`, nullable `universe_id`, `started_at`/`finished_at`, `total`/`succeeded`/`failed` counters) and `ingestion_run_items` (one row per instrument: `status`, `bars_stored`, nullable `message`, unique `(ingestion_run_id, instrument_id)`). Item FKs cascade; `ingestion_runs.universe_id` is nullable with `nullOnDelete` so run history survives a universe removal.
- `App\Enums\IngestionRunStatus` is `queued -> running -> completed`, with `failed` (nothing succeeded) and `partial` (some instruments failed) as the terminal outcomes of a finished run; `App\Enums\IngestionRunItemStatus` is `success`/`failed`. Models `IngestionRun` (belongsTo `Universe`, hasMany items) and `IngestionRunItem` (belongsTo run/instrument) cast the enums and the counters/dates.
- Shared ingestion logic lives in `App\Services\Ingestion\InstrumentIngestor`: `ingest(Instrument): int` returns the bars stored, `ingestDetailed(Instrument)` also returns the skipped malformed-row count. Both wrap the engine fetch + idempotent `daily_bars` upsert; an empty engine payload raises `App\Exceptions\EmptyIngestionResponseException`. `ingestion:scrape` uses `ingestDetailed`, so the single-ticker behavior is unchanged.
- Shared run orchestration lives in `App\Services\Ingestion\IngestionRunner`: `prepareUniverseRun($slug)` / `prepareRetryRun($runId)` resolve the scope and create a `queued` run row (throwing, with no row, for an unknown universe/run), `process($runId, $instrumentIds)` sets it `running` + `started_at`, records a `processing` item before each EOD query, then updates it to `success` with `bars_stored` or `failed` with its message. It finalizes (`completed` when `failed=0`, `failed` when `succeeded=0`, otherwise `partial`) with `finished_at`. `startUniverseRun()` / `startRetryRun()` compose prepare + process synchronously.
- `php artisan ingestion:run {--universe=sp500} {--retry=<runId>}` is a thin wrapper over the runner: it prints the summary, one line per failed instrument, and maps the terminal status to the exit code. `--retry` creates a NEW run containing only the previously failed instruments of the referenced run and inherits its `universe_id`; succeeded instruments are never reprocessed.
- Exit codes: `0` for `completed`/`partial`, `1` for a `failed` run or a pre-flight error (unknown universe slug or retry run id, no run row created). Scheduling (`ingestion-scheduler`) and the admin panel (`admin-ingestion-panel`) are separate surfaces over this ledger and never redefine its lifecycle.

## Indicators Path

- **Chinese wall — engine computes, Laravel persists.** The engine receives a bar series and returns one Indicator Snapshot per bar; it has **no** database access. Laravel (the DB owner) persists the snapshots into `indicator_snapshots`.
- **Engine math (`engine/app/indicators/`).** `core.py` holds pure, stdlib-only per-indicator functions over plain lists: `sma` (20/50/200), `ema` (21/55), `rsi` (14, Wilder), `macd` (12/26/9 line/signal/histogram), `adx` (14, Wilder), `bollinger` (20/2, population std dev) and `rvol` (current volume vs the previous 50-session average). `snapshots.py::compute_snapshots(bars)` returns a value-aligned `Snapshot` per bar. No pandas/numpy; the math is deterministic.
- **Insufficient history is `null`, never a wrong value.** Every function returns a value-aligned list and emits `None` wherever the window is not fully available (e.g. `sma200` before bar 200, `macd_signal` before bar 34, `adx` before bar 28, `rvol` before bar 51). `POST /indicators/compute` serializes those as JSON `null`s; pydantic validation rejects a malformed body with `422`.
- **Laravel persistence.** `App\Services\Engine\EngineClient::computeIndicators(array $bars)` POSTs `{bars: [...]}` to `/indicators/compute` and returns `{snapshots: [...]}`. `php artisan indicators:compute {--ticker=} {--universe=}` loads an instrument's `DailyBar`s ordered by date, calls the engine, and upserts one `IndicatorSnapshot` per `(instrument_id, date)` inside a transaction, keying the date with `Carbon::parse($date)->startOfDay()` so re-runs are idempotent. `--ticker` targets one instrument; otherwise `--universe` (default `sp500`) targets every member that has stored bars. Nothing is written when the engine fails.
- Tests never use the network: the engine math/endpoint tests read the committed fixtures (`engine/tests/fixtures/indicator_series.csv`, `indicator_constant.csv`, `stooq_nvda.csv`) and Laravel uses `Http::fake`.

## Signals Path

- **Chinese wall — engine detects, Laravel replaces.** The engine evaluates the fixed signal rules on the bar series and returns only the signals that hold on the **as-of bar** (the latest bar); it has **no** database access. Laravel (the DB owner) keeps `signals` as the *current active* set per instrument.
- **Engine rules (`engine/app/signals/`).** `rules.py` holds the 9 pure, stdlib-only predicates in one `RULES` registry (`golden_cross`, `death_cross`, `ma_alignment_bullish`, `ma_alignment_bearish`, `pivot_breakout_rvol`, `rsi_overbought`, `rsi_oversold`, `macd_bullish_cross`, `macd_bearish_cross`). Each takes the `Snapshot` for the as-of bar plus the previous bar (and the bars for the pivot) and returns `(fired, metadata)` or `None` when a needed indicator is unavailable. `detect.py::detect_signals(bars)` computes snapshots with the existing indicator math and evaluates every rule at the last index; fewer than two bars yields `[]`.
- **Fixed rules/thresholds:** SMA50/200 and EMA/MACD crosses need the previous bar; alignment is `sma20 > sma50 > sma200` (or reversed); `pivot_breakout_rvol` needs `close > max(high)` of the prior 20 sessions and `rvol >= 2.0`; `rsi_overbought` is `rsi14 >= 70`, `rsi_oversold` is `rsi14 <= 30`. Crosses/alignment use strict inequalities (equality is no signal); a null indicator never fires. Signals are date-stamped with the as-of bar date.
- **Engine endpoint.** `POST /signals/detect` accepts `{bars: [...]}` and returns `{signals: [{date, type, metadata}]}` (pydantic-validated; a malformed body is a controlled `422`; an empty series returns `{signals: []}`).
- **Laravel persistence (replace semantics).** `App\Services\Engine\EngineClient::detectSignals(array $bars)` POSTs to `/signals/detect`. `php artisan signals:detect {--ticker=} {--universe=}` loads an instrument's `DailyBar`s ordered by date, calls the engine **before** touching the stored rows (an engine failure leaves the previous set intact and exits `1`), then inside one transaction deletes every `Signal` for the instrument and inserts the freshly detected set (date keyed with `Carbon::parse($date)->startOfDay()`, metadata numeric only, deduped by type). Re-running the same bars is idempotent and a signal that no longer holds disappears. A unique key on `(instrument_id, date, type)` enforces one row per type per instrument/date.
- Tests never use the network: `engine/tests/test_signals.py` is offline (synthetic `Snapshot`s, crafted bars, committed fixtures) and Laravel uses `Http::fake`.

## Patterns Path

- **Chinese wall — engine detects, Laravel replaces** (same as signals). `POST /patterns/detect` takes `{bars}` and returns `{patterns: [{type, status, as_of_date, start_date, end_date, breakout_level, points: [{date, price, role}], metadata}]}`; the engine has no database access.
- **Engine (`engine/app/patterns/`).** `swings.py` finds strict swing highs/lows (`k = 5`, ties are not swings, the last 5 bars can never be swings). `rules.py` holds one detector per type of the first batch (`double_top`, `double_bottom`, `cup_with_handle`, `bull_flag`) and `extended.py` the second batch (`triple_top`, `triple_bottom`, `inverse_cup_with_handle`, `bear_flag`, `bull_pennant`, `bear_pennant`, reusing the same `PatternParams`; `ALL_DETECTORS` is the registry), with the documented (calibrated) parameters as named constants, returning the most recent instance still active on the as-of bar; `detect.py` scans the last 330 bars (fewer than 60 bars → none), applies the precedence rule (`apply_precedence`: triple over double, pennant over flag) and uses `core.rvol` for the cup breakout volume. Status is `forming` (no breakout yet) or `confirmed` (breakout close within the last 10 sessions); invalidated or older patterns are not returned. `breakout_level` (neckline or pivot) is the only price line; no target is ever computed.
- **Laravel persistence.** `EngineClient::detectPatterns()`; `php artisan patterns:detect {--ticker=} {--universe=}` fetches before deleting, then replaces the instrument's `chart_patterns` rows in one transaction (types/statuses outside the vocabulary and malformed points are dropped). Unique `(instrument_id, as_of_date, type)`; `ChartPattern` model, `Instrument::chartPatterns()`.
- **Calibration (chart-patterns-calibration, CLI only).** `rules.py` also exposes the parameters as a frozen `PatternParams` (defaults = the constants, `DEFAULT_PARAMS`); `near_misses.py` reruns each detector with exactly one rule relaxed (relaxations exist only for the first four types; the second batch has none yet) (fixed table, first hit per type, only for types the production rules do not detect) behind `POST /patterns/near-misses`, and `GET /patterns/parameters` returns the production values. `php artisan patterns:review-sample {--per-type=40} {--negatives=40} {--out=storage/app/pattern-review} {--seed=} {--universe=sp500} {--force}` exports detected rows from `chart_patterns` (balanced forming/confirmed, seeded) plus near misses (round-robin over types) as `sample.csv` (`id, ticker, type, status, as_of, points, suggested_label, label, notes`; near misses have status `near_miss:<rule>`), one standalone SVG per case (`App\Services\Patterns\PatternReviewChart`), `parameters.json` and labelling `README.txt`. `php artisan patterns:calibration-report {csv} {--universe=}` prints markdown: precision per type, miss rate per type/rule, suggested-label agreement, frequency over the current `chart_patterns` set and the parameters (`parameters.json` next to the CSV, else the engine). Samples live under `docs/calibration/`.
- **Pipeline.** `ingestion:pipeline` runs `patterns:detect` after `signals:detect`; a failure there makes the pipeline exit `1` without undoing earlier stages. `db:copy-sqlite-to-pgsql` skips `chart_patterns` (derived data).

## Alerts Path

- **Rules.** `alerts` rows (`App\Models\Alert`, owned by `user_id`, not fillable) of three kinds: `screener_new_candidates` (one per Saved Screener, FK cascade), `watchlist_signal` (one per user, chosen Signal types) and `watchlist_pattern` (one per user, alerts-patterns: `pattern_types` ⊂ `ChartPattern::TYPES` and `pattern_events` ⊂ `['appears', 'confirmed']`, both JSON in canonical order, null for the other kinds; events default to `['confirmed']`). Max `config('alerts.max_per_user')` (10) per user across kinds.
- **Pattern alerts.** The evaluator dispatches with an explicit `match` on kind. A `watchlist_pattern` state is `{patterns: {TICKER: {type: {start, status}}}}` read from the current `chart_patterns` rows of followed Instruments (chosen types only). Pattern identity is `type + start_date` (first key point). `appears` fires for an instance absent before (new row or new `start`); `confirmed` fires when an instance is confirmed now and was not confirmed before; both at once yield one `confirmed` item. Disappearance, expiry and invalidation never notify; a reappearance notifies again. Items add `status` and `breakout_level` and use `reason` `pattern:<type>:<event>`.
- **Evaluation.** `App\Services\Alerts\AlertEvaluator` runs once per as-of date (the latest stored Daily Bar date). The first evaluation stores a baseline in `last_state` without notifying; later ones notify only additions (new Candidates from the shared `App\Services\Screener\CandidateQuery`, or chosen Signal types newly active on a followed Instrument) and replace `last_state`. Notification and state update share one transaction. `php artisan alerts:evaluate` evaluates every active alert, isolating failures (exit `1`), and is the last stage of `ingestion:pipeline`, run only when `signals:detect` succeeded.
- **Notifications.** Laravel database notifications (`notifications` table, `App\Notifications\AlertTriggered`, database channel only) with language-neutral data `{alert_id, kind, as_of, saved_screener_id/name, items: [{ticker, name, reason}] (max 50), more}` (pattern items also carry `status` and `breakout_level`). `notifications:prune` deletes those older than `config('alerts.notification_retention_days')` (90) daily at 03:20.
- **API (`auth:sanctum`).** `GET/POST /api/alerts`, `PATCH/DELETE /api/alerts/{id}` (foreign id `404`; limits/duplicates `422`; re-activating or changing signal types, pattern types or pattern events to a different set resets the baseline; every alert payload has `pattern_types`/`pattern_events`, null for non-pattern kinds), `GET /api/notifications` (20 per page, newest first, `unread_count`) and `POST /api/notifications/read` (`ids` or `all`).
- **SPA (alerts-ui).** `alertsApi`/`notificationsApi` in `frontend/src/lib/api.ts` mirror that contract (CSRF before writes). `UnreadNotificationsProvider` (`frontend/src/notifications/`, mounted in `AppLayout`) holds the shared unread count: fetched from `GET /api/notifications` on sign-in, on every route change and on `refresh()`; the inbox sets it after its own fetch and after mark-read (no polling or live updates). The Portal loads the alert list once (`components/portal/usePortalAlerts.ts`): each Saved Screener row has a `role="switch"` "Avisarme de nuevos candidatos" toggle (`ScreenerAlertToggle`: create, pause via `PATCH active=false`, resume, remove), and `WatchlistAlertForm` edits the single `watchlist_signal` alert (9 Signal types, save disabled while none is selected, pause/resume/delete); below it `WatchlistPatternAlertForm` ("Mis alertas de patrones") edits the single `watchlist_pattern` alert (4 pattern types, events "Cuando aparece"/"Cuando se confirma (ruptura)" with confirmed pre-ticked, save disabled without a type and an event or when unchanged). API `422` messages (limit, duplicate) show inline. The inbox renders text from the neutral data (`reason` `new_candidate`, a Signal type, or `pattern:<type>:<event>` shown as pattern label · event · "Ruptura <formatPrice>", with "Patrones en tu Watchlist" as the title of `watchlist_pattern` notifications) and links each ticker to `/instruments/{ticker}`, where the current patterns are drawn.
- **Daily email digest (alerts-email-digest).** Off unless `AlertEmailDigestAvailability::available()`: the flag `ALERT_EMAIL_DIGEST_ENABLED` plus the provider name and location, which `GET /api/legal` returns as `email_digest` so the privacy policy names them. Opt-in: `GET/PUT /api/alerts/email` (`AlertEmailPreferenceController`; `users.alert_email_opt_in_at` and `preferred_locale` from `Accept-Language`; opting in while unavailable is a `409`). After evaluating, `alerts:evaluate` calls `AlertDigestSender::queue($asOf)` inside a try/catch: for each opted-in user with notifications of that as-of, it creates an `alert_email_digests` ledger row (unique `user_id, as_of`) and dispatches `App\Jobs\SendAlertDigest` on the `database` queue (3 tries, backoff 60/300 s). The job re-checks the opt-in and availability, builds `AlertDigestContent` in the user's language (at most 50 instruments; `lang/{es,en}/alert_email.php` mirrors the inbox wording) and sends `App\Mail\AlertDigest`: HTML and text parts, no images or tracking, `List-Unsubscribe` and `List-Unsubscribe-Post` headers. `sent_at` is set only after the transport accepts the message. Unsubscribe: `GET/POST /api/email/alerts/unsubscribe/{user}` with a relative signature (`signed:relative`, rooted at APP_URL); GET renders `alert-email-unsubscribed` in the user's language, POST answers 204. The ledger is pruned by `model:prune` and cascades with the account; the account export includes it as `alert_emails`.
- **Screener extraction.** `CandidateQuery::candidates(Universe, filters)` holds the Screener's matching, payload and ranking, used by `ScreenerController` and the evaluator; `CandidateQuery::fromSaved()` normalizes a stored Saved Screener definition.

## Scheduling (Daily EOD Pipeline)

- **Schedule location.** The single scheduled event is registered in `routes/console.php` with the `Illuminate\Support\Facades\Schedule` facade (the `commands:` file already passed to `withRouting()` in `bootstrap/app.php`, which is unchanged). `php artisan schedule:list` shows one event named `ingestion-pipeline`.
- **Market timezone / DST.** `config/app.php` stays **UTC**. The event carries `->timezone(config('ingestion.timezone'))` (default **`America/New_York`**), so the wall-clock run time is interpreted in market local time and the UTC fire instant shifts by an hour across DST. The tz database handles EST/EDT.
- **Configured time.** `config/ingestion.php` holds `timezone` (`INGESTION_TIMEZONE`), `market_close` (`INGESTION_MARKET_CLOSE`, default `16:00`), `schedule_buffer_minutes` (`INGESTION_SCHEDULE_BUFFER_MINUTES`, default `30`), `universe` (`INGESTION_UNIVERSE`, default `sp500`) and `lock_ttl_seconds` (`INGESTION_LOCK_TTL_SECONDS`, default `7200`). The event fires at `market_close + buffer` = `dailyAt('16:30')` → expression **`30 16 * * 1-5`**. Note `schedule:list` displays times converted to `config('app.timezone')` (UTC) unless `--timezone=America/New_York` is passed; the event's raw expression is `30 16 * * 1-5`.
- **Market calendar / holidays.** `App\Services\Market\MarketCalendar` is a pure helper (`isHoliday`, `isTradingDay`) reading the committed `config('ingestion.holidays')` list (current + next year NYSE dates, `Y-m-d`). Weekends are excluded by `->weekdays()`; holidays are excluded at the schedule level with `->skip(...)` **and** re-checked inside the wrapper (`isTradingDay`) as defense in depth. Half-days (early closes) are trading days and are not listed. The list is a committed snapshot, not a computed calendar, and must be refreshed annually.
- **Composition.** `php artisan ingestion:pipeline {--universe=} {--force}` is a thin wrapper: it calls `ingestion:run` → `indicators:compute` → `signals:detect` → `patterns:detect` → `screener:refresh` → `alerts:evaluate` (the last only when signals and the refresh succeeded) via `$this->call()`. The commands keep their own behavior, signatures and ledgers unchanged. If ingestion fails (a `failed` run, exit `1`), later stages are skipped; if a later stage fails, the remaining stages are still attempted and the pipeline exits `1`. It exits `0` on success and on a skip.
- **Overlap.** The event uses `->withoutOverlapping(120)` (scheduler mutex) and the wrapper additionally holds an atomic `Cache::lock('ingestion:pipeline', config('ingestion.lock_ttl_seconds'))`. A second invocation prints "already running" and exits `0` (a skip, not a failure). Locks require a cache store that supports them (`database` in dev, `array` in tests); a crashed run holds the lock until the TTL.
- **Manual recovery, no catch-up.** A missed run is triggered manually with `php artisan ingestion:pipeline` (full) or the existing `php artisan ingestion:run` (ingestion only). `--force` bypasses the trading-day guard for manual recovery. There is no backfill/"run if late" logic; `schedule:run` does not backfill a missed minute.
- **Production.** The schedule only defines when to run; production still needs a host cron / Task Scheduler entry running `php artisan schedule:run` (a deployment concern). `init.ps1` starts no scheduler or daemon.

## Admin Ingestion Panel

- **Server-side boundary.** All four endpoints live in the existing `Route::middleware(['auth:sanctum', 'admin'])->prefix('admin')` group in `routes/api.php`: guests get **401**, authenticated non-admins get **403**. The SPA hides the Admin tab for non-admins and guards the page, but that is a UI affordance only — the API is the enforcement point. Existence checks happen in the controller (not implicit route-model binding) so an unknown run id still returns the 401/403 contract for a non-admin and `404` only for an admin.
- **Endpoints** (`app/Http/Controllers/Admin/IngestionRunController.php`):
  - `GET /api/admin/ingestion/runs?limit=20` -> `200 {runs: [run]}` newest first, without items, each with `universe`.
  - `POST /api/admin/ingestion/runs` body `{universe?: string}` (default `config('ingestion.universe')`) -> `202 {run}`; `422` for an unknown universe.
  - `GET /api/admin/ingestion/runs/{run}` -> `200 {run}` including `items` ordered by instrument ticker; `404` unknown.
  - `POST /api/admin/ingestion/runs/{run}/retry` -> `202 {run}` (the new run); `404` unknown; `422` when the run is not terminal or has no failed items.
  - `run = {id, status, universe:{id,slug,name}|null, started_at, finished_at, total, succeeded, failed}`; `item = {id, ticker, status, bars_stored, message}` (explicit arrays; the repo has no API resource classes).
- **Execution model.** The trigger resolves the scope, creates the `queued` `ingestion_runs` row and dispatches `App\Jobs\RunIngestionJob` (carrying the run id + instrument ids), then returns `202` immediately. The database queue worker (`php artisan queue:work`) calls `IngestionRunner::process()`, which moves the run `queued -> running -> completed|partial|failed`; each active EOD query is visible as a `processing` log item. `RunIngestionJob` has `$tries = 1`, so a failed run is never silently re-executed. `.env.example` defaults `QUEUE_CONNECTION=database`; `init.ps1` starts no worker.
- **Observation.** No SSE/WebSockets and no job-progress API: while the selected run is non-terminal the SPA polls `GET /api/admin/ingestion/runs/{id}` every ~2500 ms and renders the embedded `items` as the log. A run stuck in `queued` is treated as a normal pending state (hint + keep polling), never an error.
- **Retry.** Reuses the `ingestion:run --retry` semantics exactly (new run, only previously failed instruments, inherited universe). The controller rejects a non-terminal run or one with no failed items with `422` before the runner is called.
- **UI.** `frontend/src/pages/AdminPage.tsx` (guard + trigger + telemetry tiles + history + polled log) with `frontend/src/components/admin/{RunStatusBadge,RunTelemetry,RunHistoryTable,RunLogStream}.tsx`; `AuthUser.role` and `NAV_ITEMS[].adminOnly` drive tab filtering. Only real ledger data is shown — the prototype's proxy/worker/cache tiles are not requirements.
- **Panel scope.** The panel triggers the **ingestion stage / ledger**, not `ingestion:pipeline`; the daily scheduler still owns the full ingest -> indicators -> signals pipeline.

## Instrument Detail API

- **Route.** `GET /api/instruments/{ticker}` is a top-level public route in `routes/api.php` carrying only the `api` middleware — no `auth:sanctum`, no `admin`, no route-model binding and no `where` constraint (tickers may contain `.`/`-`, e.g. `BRK.B`). Browsing charts requires no session (`docs/user-and-access-model.md`) and the data is system-owned public market data, so there is no authorization branch.
- **Lookup.** The path value is normalized with `trim` + `strtoupper` before an exact `instruments.ticker` lookup, so matching is case-insensitive; inactive instruments are still returned (a removed instrument keeps its history per `docs/domain-model.md`). An unknown ticker returns HTTP `404` with the explicit JSON body `{"message":"Instrument not found."}` (a controller response — never `firstOrFail`, never a 500).
- **Bounding.** `?limit=` is optional, defaults to **252** (one trading year of sessions) and is clamped silently to **`1..2000`** (never a `422`); a non-numeric value falls back to the default. The limit selects the **most recent** bars, which the payload then presents **ascending by date** so a candle chart renders left-to-right.
- **Payload** (`app/Http/Controllers/InstrumentController.php`, explicit arrays, no Resource classes): `{instrument, bars, snapshot, signals, patterns, meta}`; `patterns` = active chartist patterns `{type, status, start_date, end_date, breakout_level, points: [{date, price, role}]}` ordered by type (no target field).
  - `instrument = {ticker, company, sector, exchange, active}`.
  - `bars = [{date, open, high, low, close, volume}]` — `date` is `Y-m-d`; OHLC are JSON numbers and `volume` an integer.
  - `snapshot` = the `indicator_snapshots` row with the greatest `date` (unique per `(instrument_id, date)`, so no tie), the full indicator key set plus the as-of `date`, or `null` when the instrument has no snapshot. Every indicator key is always present (`null` when history was insufficient, matching `indicators-compute`).
  - `signals = [{type, date, metadata}]`, the current active set ordered by `type` ascending; `[]` when none.
  - `meta = {limit, bar_count, latest_bar_date}` (`latest_bar_date` is `null` when the instrument has no bars).
- **Numbers at the boundary, `decimal` in storage.** `decimal:4` cast values are converted with `(float)` when shaping the payload, so the client receives JSON numbers while the columns and the `decimal` storage rule are unchanged (`CONSTRAINTS.md`). A whole-number decimal (e.g. `175.0000`) serializes as the JSON number `175`, which JS consumers treat as a number.
- **No per-bar indicator series.** Only the **latest** snapshot is returned; SMA/EMA/Bollinger series per bar are intentionally a `chart-interactive` concern (future hook), not part of this contract. `watchlist` can reuse this endpoint; no ownership is involved.

## Screener API

- **Route.** `GET /api/screener` is a top-level public route in `routes/api.php` carrying `api` + `throttle:60,1` only — no `auth:sanctum`, no `admin`, no controller authorization branch. Browsing the Screener requires no session (`docs/user-and-access-model.md`); the throttle implements that document's "anonymous users may hit rate limits" edge case. `limit` is the only silently clamped param; every other param can change which rows are returned or their order, so a bad value is a `422` (`CONSTRAINTS.md` -> Public API).
- **Contract** (`app/Http/Controllers/ScreenerController.php`, explicit arrays, no Resource classes): `{universe: {slug, name}, sort, candidates, meta: {limit, returned, total}}` (this is the contract `screener-filters-ui` and `candidate-list-ranking` consume).
  - `universe` = the `universes` row resolved by `slug`, defaulting to `config('ingestion.universe')` (currently `sp500`). An unknown slug is an explicit JSON `404 {"message":"Universe not found."}`; a valid universe that matches nothing is a `200` with `candidates: []` (the empty case must never be blurred with an error).
  - `candidate = {ticker, company, sector, exchange, active, date, close, change_percent, rvol, rsi14, signals, patterns}`; `patterns` = the active chartist patterns as `{type, status, breakout_level, end_date}` ordered by type (`[]` when none). `date` is the latest Daily Bar date; `close`/`rvol`/`rsi14`/`change_percent` are JSON numbers or `null` (insufficient history); `signals` are the active `type` strings ascending (`[]` when none). `active` is returned but is **not** a filter (pivot membership is the universe criterion; detachment is how an instrument stops producing Candidates).
  - `meta.limit` = the clamped limit, `meta.offset` = rows skipped, `meta.total` = rows matched before paging, `meta.returned` = rows returned.
- **Pagination.** `?offset` (default 0) skips that many ranked candidates; like `limit` it is clamped silently (missing, non-numeric or negative → `0`, never a `422`) and an offset past the end returns an empty page with the real `total`. The SPA keeps `page` (1-based) and `limit` (25/50/100/200, default 50) in the URL (`frontend/src/lib/screenerPagination.ts`), sends `limit` + `offset`, shows `Mostrando {from}–{to} de {total}` and a `ScreenerPagination` bar (Anterior/Siguiente, `Página N de M`, page size). Filter, ranking or page-size changes restart at page 1; a stale page past the end jumps to the last page (or drops `page` when nothing matches); page changes are history entries. The buttons are only disabled at the first/last page, never while loading, so keyboard focus stays on them.
- **Filters (all AND; the `signal` and `pattern` lists are OR).** `signal` (one or more of the 9 fixed types, comma-separated and/or array form; unknown type `422`), `pattern` (one or more of the 4 pattern types, same forms; unknown `422`) narrowed by `pattern_status` (`any` default, `forming`, `confirmed`; other values `422`; ignored without `pattern`), `rsi_min`/`rsi_max` on latest `rsi14` (inclusive), `min_rvol` on latest `rvol` (inclusive), `price_above_sma200` (`latest close > sma200`, both non-null), `ma_cross` (`bullish`: `sma50 > sma200`; `bearish`: `sma50 < sma200`; equality/null excluded). A `null` indicator never satisfies a numeric/derived filter. An explicit `rsi_min > rsi_max` is valid and simply matches nothing. `limit` defaults to **50** and is clamped to **`1..500`** (a non-numeric value falls back to the default; never a `422`).
- **Candidate selection.** The base set is universe members that have **both** at least one `daily_bars` row and at least one `indicator_snapshots` row; a member missing either is excluded even with no filter, because it cannot produce the candidate fields.
- **Precomputed rows (screener-precomputed).** `screener_rows` holds one row per Instrument that has a latest Daily Bar and Indicator Snapshot: ticker/company/sector/exchange/active, latest `date` and `close`, `previous_close` (second latest bar by date), `change_percent`, `rvol`, `rsi14`, `sma50`, `sma200`, `price_above_sma200`, `ma_cross`, `signal_count`, `signals` and `patterns` (json, the candidate payload lists). `App\Services\Screener\ScreenerRowBuilder::refresh()` (`php artisan screener:refresh`) rebuilds it in one transaction (upsert + delete rows of instruments that no longer have a bar and a snapshot) and runs in `ingestion:pipeline` (after patterns, before alerts), at the end of every ingestion run (`IngestionRunner::process`: Admin job, `ingestion:run`, retries), after `ingestion:scrape`, after the S&P 500 seeder and in `deploy/deploy.sh` (before and after activation); running `indicators:compute`, `signals:detect` or `patterns:detect` by hand needs a `screener:refresh` afterwards. `change_percent` is stored as a 17-significant-digit string because Laravel binds floats with 14 digits, which would turn near-equal values into ties.
- **Loading / no N+1.** `CandidateQuery` filters the rows of the Universe's members in SQL (`EXISTS` on `signals` / `chart_patterns` for the OR lists and pattern status; indexed comparisons, nulls never match), counts the total, orders by the sort key nulls last plus `ticker` in byte order (`COLLATE "C"` on PostgreSQL) and applies `offset`/`limit`. A request costs a handful of queries whatever the universe size (about 11–19 ms for 5,494 instruments in a local scale test). `change_percent` in the payload is recomputed from the stored decimals, so the JSON is identical to the former per-request computation (old vs new: 540 filter/sort/page combinations on real data and 784 adversarial cases, 0 differences). `test_candidate_loading_does_not_scale_queries_with_universe_size` guards the constant query count.
- **`change_percent`.** `((latest close - previous close) / previous close) * 100` from the two most recent stored Daily Bars by date; `null` when the instrument has fewer than two bars or the previous close is `0`. Not rounded; it stays a JSON number or `null`.
- **Sorting (server-side, deterministic).** `rvol_desc` (default), `rsi_desc`, `rsi_asc`, `change_desc`, `change_asc`, `signal_count_desc` (count of active signal types). Every order applies **nulls last** and a **ticker ASC tie-break**, so equal keys never produce a non-deterministic ranking.
- **Numbers at the boundary, `decimal` in storage.** `decimal:4` cast values are converted with `(float)` when shaping the payload, so the client receives JSON numbers while the columns and the `decimal` storage rule are unchanged. A whole-number decimal (e.g. `105.0000`) serializes as the JSON number `105`, which JS consumers treat as a number.
- **Shared filter parser.** `App\Services\Screener\ScreenerFilterParser::fromArray()` owns the filter vocabulary (`SIGNAL_TYPES`, `PATTERN_TYPES`, `PATTERN_STATUSES`, `MA_CROSSES`, `SORTS`) and its `422` rules. `ScreenerController` passes it the query string; the natural-language interpreter passes it the AI answer, so both paths accept exactly the same filters (`ai-screener-natural-language`). `ScreenerApiTest` is the regression net for the extraction.

## Screener UI

- **Route.** `/` is the product's primary surface (`frontend/src/pages/ScreenerPage.tsx`); the former `/screener` path redirects to `/` with its query and hash preserved. It is **anonymous** — the page never calls `useAuth`, never redirects for authentication and never prompts for login (`docs/user-and-access-model.md`). `GET /api/screener` remains the only data source and needs no session. The user manual is available at `/como-funciona` and linked from the Screener header.
- **URL is the screener state source of truth.** The eight criteria plus the ranking key `sort` live in the query string (`useSearchParams`) using the API's own param names, so the URL is directly usable as an API call and is shareable/deep-linkable. `frontend/src/lib/screenerFilters.ts` owns the round-trip: `parseScreenerFilters` is strict and lenient (unknown/invalid values are dropped, so a hand-edited URL can never produce a `422`; an absent or unknown `sort` resolves to `DEFAULT_SCREENER_SORT = 'rvol_desc'`), `patchScreenerFilters` writes only the nine owned keys (`signal`, `rsi_min`, `rsi_max`, `min_rvol`, `price_above_sma200`, `ma_cross`, `pattern`, `pattern_status`, `sort`; the default `pattern_status=any` is omitted) and preserves unrelated params (the default sort is **deleted** from the URL so an unmodified ranking keeps it clean), and `screenerFiltersKey` is the deterministic key for the fetch effect, including `sort`. All URL writes use `replace: true` so changes do not flood browser history. `sort` is a ranking preference, not a criterion: `hasActiveFilters`/`countActiveFilters` ignore it and "Limpiar filtros" applies `EMPTY_SCREENER_CRITERIA` (the eight criteria only), so the selected order survives a clear.
- **Request.** `frontend/src/lib/api.ts` exposes `screenerApi.search(filters, signal?)`, which serializes the active criteria **plus `sort` on every request** (never `limit`/`universe`) and calls `GET /api/screener`. The page aborts the in-flight request with an `AbortController` when the URL state changes (ignoring `AbortError`) and suppresses an identical repeated query. The numeric RSI inputs are uncontrolled drafts committed on blur/Enter, so typing never fires a request per keystroke. There is no auto-retry.
- **States.** `loading` (first request, skeleton), `refreshing` (previous list kept with an "Actualizando…" indicator and `aria-busy`), `ready` (table, or an empty panel split into "no match" vs "no EOD data yet"), and `error` (`role="alert"` with the API message + a manual "Reintentar"). A valid-but-empty `200 candidates: []` is never shown as an error. A results header is rendered on **every** status so the ranking control is always reachable; it shows the ranking `<select>` (`frontend/src/components/screener/ScreenerSortControl.tsx`, the six API sorts with a native `<label>` + `<select>`), and, once data exists, a read-only Universe chip (from `response.universe.name`) and `Mostrando {returned} de {total} candidatos`. The control is driven by the URL-owned `sort`, not by `response.sort`, so it restores from a deep link and updates instantly.
- **Patterns.** The filter panel has a "Patrones chartistas" chip group (4 types, OR) and a status segmented control (`Cualquiera`/`En formación`/`Confirmado`) that is disabled until a pattern is selected; removing the last pattern resets the status to `any`, and a status without patterns (deep link or stored row) is read as `any`. Candidate rows show pattern badges (`label · status` as text, dashed border) next to the signal badges. Saved Screeners store and restore both keys.
- **Server-side only.** Filtering and ranking belong to the Screener API; the SPA sends `sort=<value>` and renders the API's `candidates` order with **no client-side comparator**. The compact Saved Screeners disclosure (below the filter panel) and the Candidate-row "Ficha IA" link (rendered by `CandidateTable` only when `CandidateResults` passes `showCompanyCardLink={useSignedIn()}`, so Visitors and the auth-loading state never see it) are the only auth-aware affordances on the page; chart navigation (`chart-interactive`), the watchlist and a universe selector are separate features.
- **Natural-language input** (`frontend/src/components/screener/ScreenerAiQuery.tsx`, above the filter panel). Signed-in only: nothing while auth loads, a sign-in link for a Visitor, a not-available notice after `provider_not_configured`. On submit it calls `screenerApi.interpret()` and applies the answer through `interpretedFiltersToPatch()` (the Saved Screener deserializer) with the page's usual `patchScreenerFilters` + `resetScreenerPage` path; it keeps the previous `URLSearchParams` for Undo. Explanation and unsupported parts are plain text.

## Chart UI

- **Routes and entry.** `/instruments/:ticker` is the canonical per-instrument deep link and `/chart` remains a legacy no-ticker guidance route (no API request). Both mount `frontend/src/pages/InstrumentChartPage.tsx` inside the shell. The primary entry is the ticker cell of each `CandidateTable` row (`react-router` `<Link to={'/instruments/' + encodeURIComponent(ticker)}>`); Watchlist tickers also link to charts. There is no Chart tab. The page is **anonymous**: it never calls `useAuth`, never redirects and never prompts for login (`docs/user-and-access-model.md`). Visitors do not see the Jev forecast and AI Company Card panels: both read the session with `useSignedIn` (`frontend/src/auth/useSignedIn.ts`, non-throwing, no fetch) and render nothing for a Visitor or while auth is loading.
- **Charting library (self-hosted, decided).** `lightweight-charts` (TradingView Lightweight Charts) is added to `frontend/` as a pinned dependency (**5.2.1**, Apache-2.0, runtime dep `fancy-canvas@2.1.0` MIT). The **embedded TradingView widget is not used**. The library's `layout.attributionLogo` option stays **enabled** (its default): the Apache-2.0 NOTICE requires the TradingView attribution link on the page that shows the chart. The chart is lazy-loaded (`React.lazy`) as its own Vite chunk so the Screener bundle stays lean.
- **Data source (frozen).** The only source is `GET /api/instruments/{ticker}` via `frontend/src/lib/api.ts` -> `instrumentApi.detail(ticker, {limit})`; the page always requests `?limit=CHART_BAR_LIMIT` (`252`). The API returns the most recent N bars **ascending by date** and the SPA renders that order as-is (no re-ordering, no client-side fetch inside the chart component).
- **Chart contents.** A `CandlestickSeries` for the bars; a `HistogramSeries` in **pane index 1** for volume, one bar per Daily Bar colored by candle direction (`gain`/`loss`); horizontal **price lines** for the latest non-null `sma20`/`sma50`/`sma200` (`SMA 20`/`SMA 50`/`SMA 200`) and for the active `pivot_breakout_rvol` signal's `metadata.pivot` (title `PIVOTE`). Active chartist patterns add key-point markers (`createSeriesMarkers`, short role labels, only on loaded bars) and one dotted `breakout_level` price line titled with the pattern name. The page also renders a mono OHLC/legend strip (last bar + SMA values + pivot), a textual "Señales activas" panel and a "Patrones activos" panel (`PatternPanel`: status, dates, breakout level and named points), because the canvas is not screen-reader navigable.
- **No client-side indicator math.** The engine owns indicator computation (`CONSTRAINTS.md` -> Indicators) and the detail payload contains only the **latest** snapshot (single numbers, `null` for insufficient history). The SMA overlays are therefore horizontal reference lines at the latest values — never a computed per-bar curve. A per-bar series requires an API extension (future hook).
- **No stop/target.** Stop and target are not modeled anywhere, so the chart never draws or derives them; only the pivot is drawn. `frontend/src/lib/chartData.ts` (`toCandlestickData`, `toVolumeData`, `smaLevels`, `signalLevels`, `patternLevels`, `patternMarkers`, `hasChartData`, `insufficientHistory`, `CHART_COLORS`, `CHART_BAR_LIMIT`) is pure and React-free; canvas colors are the exact `frontend/src/index.css` token hexes.
- **Lifecycle.** One `useEffect` creates the chart, sets the data/lines and returns a cleanup that always calls `chart.remove()`, so a ticker change, unmount or React StrictMode double-invocation cannot leak a canvas or duplicate the chart. `autoSize: true` plus an explicit container height makes it resize with its card.
- **States.** `loading` (skeleton), `ready`, `not_found` (API `404 {message:"Instrument not found."}` -> "Instrumento no encontrado" + link to the Screener), `error` (`role="alert"` + manual `Reintentar`), `empty` (`bars.length === 0` -> "Sin datos EOD" and **no chart instance**) and a soft "historial insuficiente" note when `snapshot` is `null` or none of the three SMAs is available (the chart still renders). A settled result is keyed to the current ticker/retry, so a ticker change never flashes the previous instrument.

## Experimental Jev Forecast

The experimental forecast is an authenticated panel on the public Instrument chart. Laravel owns the bounded as-of state built from stored Daily Bars, same-date Indicator Snapshots and Signals; the Python engine is not involved. A server-only `JevClient` sends that state to TypeSafe AI and validates the three-class response. `forecast_predictions` stores one versioned prediction per Instrument, reference date and horizon; the user's minimum-probability preference changes only presentation. The daily pipeline resolves target-date closes, and an Admin-only report reads resolved outcomes separately from pending cases. Historical backfill is an explicit, cost-bearing command and is limited to years covered by the committed market calendar.

The Admin Backtesting tab starts an explicit historical run for 1–100 Instruments and 1–100 recent reference bars each. A run and its cases are stored in `forecast_backtest_runs`/`forecast_backtest_cases`; cases are inserted in database batches. `AdvanceForecastBacktestRun` queues one case job followed by one successor on the default FIFO worker, so newly arriving ingestion jobs can run between Jev cases instead of waiting behind thousands of them. Each case job reuses `ForecastService` and its as-of cutoff. The run pins the model and question versions; jobs with different current versions skip without making a provider call. The job requires the next trading-session Daily Bar before calling Jev, records predicted and observed classes, and updates the run's completed/skipped/correct counts. If dispatch fails, queued cases become skipped and the run becomes terminal (`failed`), allowing another attempt. A partial unique database index permits at most one queued/running backtest even if its start lock expires. The page polls a protected Admin API with 100 cases per page and computes accuracy over completed cases only. This measures direction-class accuracy, not trading returns; it is reported separately from prospective forecasts.

## AI Company Card

An authenticated, on-demand panel on the public chart page (`ai-company-card`, spec `docs/specs/ai-company-card.md`). The Python engine is not involved.

- **Client.** `App\Services\Ai\OpenAiCompatibleClient` is a generic OpenAI-compatible Chat Completions client (`{AI_BASE_URL}/chat/completions`, Bearer key, timeout) configured by `config/ai_card.php`. `structured($messages, $schemaName, $schema)` sends `response_format: json_schema` with `strict: true`; on a `400` and `AI_RESPONSE_FORMAT_FALLBACK=true` it retries **once** with `json_object` and the schema embedded in the system prompt (`AI_RESPONSE_FORMAT=json_object` skips the first attempt). It accepts only `finish_reason: stop`, no `refusal` and a JSON object (a surrounding json code fence is stripped), and returns the decoded data plus token usage, format and latency. Errors become `AiProviderException` (`provider_unavailable` / `invalid_provider_response`); logs carry only the exception class or HTTP status. A base URL that is not `https://` (or `http://` on localhost/127.0.0.1) counts as not configured.
- **Domain.** `App\Services\CompanyCard\`: `CompanyCardSchema` (the `company-card-v2` JSON Schema and a hand-written validator: exact key sets `company`, `outlook`, `limitations`, `sources` (no `metrics`/`data_as_of` since `company-fundamentals-sec`), types, enums, `horizon_months === 3`, strict caps on identifiers, ticker match; free-text fields over their cap are shortened at a sentence end or a word with an ellipsis instead of rejecting the card; strings trimmed and control characters stripped), `CompanyCardPrompt` (`company-card-prompt-v3`: summarizer of verified SEC figures, outlook grounded on them, may cite given figures with their period but never state other figures; without fundamentals it must say so in `limitations`; per-field length limits, no targets/ratings/advice), `CompanyCardContextBuilder` (Instrument identity; the SEC fundamentals block whenever a row with figures exists; price-derived metrics, latest close/change, indicators, Signals and chartist patterns only when `AI_CARD_MARKET_DATA_RIGHTS_VERIFIED=true`), `CompanyCardService` and `CompanyCardUnavailable`.
- **Flow.** `GET /api/instruments/{ticker}/company-card` -> `{card|null, available, fundamentals|null}` reads the database only (`fundamentals` comes from Company Fundamentals and is present even when the AI provider is disabled). A card is fresh only with the current model and prompt version, inside the window and with the same SEC filing accession as the current fundamentals. `POST` -> reuse a fresh card (`reused: true`) -> `provider_not_configured` unless enabled and configured -> `Cache::lock('ai-card:'.sha256(instrument|locale|schema), timeout+15)->block(timeout+10)` (timeout -> `busy`) -> re-read -> caps (`user_daily_limit` 429, `daily_limit_reached` 503; attempts since UTC midnight from the log) -> provider -> validate -> upsert the card and a `succeeded` log row in one transaction. Provider/validation failures write one `provider_error` / `invalid_response` log row and keep any older card.
- **Storage.** `ai_company_cards` (unique `instrument_id, locale, schema_version`; `prompt_version`, `model`, `context_mode`, `context_as_of_date`, `fundamentals_accession`, `fundamentals_period_end`, `content` json, `generated_at`; v1 rows stay stored but are never read) and `ai_company_card_generations` (instrument, nullable user, locale, model, versions, response format, status, error code, token counts, latency; `MassPrunable`, pruned daily by `model:prune` after `AI_CARD_LOG_RETENTION_DAYS`). For signed-in users only, `CandidateTable` links each row to `/instruments/{ticker}#ai-company-card`; the panel owns the hash scroll (once, when it first renders signed in, whichever of chart data or session resolves first). Operations: `docs/ai-company-card-operations.md`.

## Natural-language Screener

`ai-screener-natural-language` (spec `docs/specs/ai-screener-natural-language.md`).

- **Flow.** `POST /api/screener/interpret` (`auth:sanctum`, `throttle:{ai_screener.requests_per_minute},1,ai-screener`) -> `ScreenerInterpretController` -> `App\Services\Screener\Ai\ScreenerQueryInterpreter`: configuration check (`AI_SCREENER_ENABLED` + shared provider) -> cache lookup (24 h, key `sha256(normalized text, locale, schema and prompt versions)`; a hit skips caps and provider) -> rolling 24 h caps (rows with outcome `ok`/`invalid`/`pending` in `ai_screener_queries`; checked and a `pending` slot reserved under the short `ai-screener:caps` lock, so concurrent requests cannot overshoot, and the slot is updated to the final outcome after the call) -> one `OpenAiCompatibleClient('ai_screener')` call with `ScreenerQueryPrompt` (user text only in the user message, temperature 0) and the strict `ScreenerQuerySchema` -> PHP validation, then `ScreenerFilterParser` -> log row and cache store. ## Company Fundamentals (SEC)

Verified fundamentals for the Company Card (`company-fundamentals-sec`, spec `docs/specs/company-fundamentals-sec.md`), computed in Laravel; the Python engine and the EOD pipeline are not involved.

- **Client.** `App\Services\Fundamentals\SecEdgarClient` (`tickers()` from `SEC_TICKERS_URL`, `submissions($cik)` and `companyFacts($cik)` from `SEC_DATA_BASE_URL`) sends the configured `User-Agent` and `Accept-Encoding: gzip, deflate`, spaces requests through the injectable `Sleeper` (clock + sleep), retries 429/5xx/timeouts twice (2 s, 8 s), never follows redirects and raises `SecUnavailable` (`forbidden`, `not_found`, `unavailable`, `http_error`, `invalid_response`). Logs carry the endpoint kind and status only.
- **Parsing.** `CompanyFactsReader` keeps only the whitelisted concepts and 10-K/10-Q(/A) facts right after decoding (and remembers every accession in the document). `TtmCalculator` (anchor, `(start,end)` dedupe with the latest `filed`, TTM = annual fact or `A + L - C`, four-quarter fallback, prior year) and `FundamentalsExtractor` (concept chains, financial SIC 6000-6411, debt/cash/equity at the newest equity date, shares from `dei` cover / balance sheet / weighted average, DPS chain) are pure; `inputs` keeps provenance per input.
- **Refresh.** `php artisan fundamentals:refresh {--ticker=*} {--force}` (`RefreshFundamentals` + `FundamentalsRefresher`): refuses (exit 1, no request) unless enabled with a valid UA; `Cache::lock('fundamentals:refresh')` (held -> skip, exit 0); SEC ticker map cached 7 days (`BRK.B` -> `BRK-B`); Instruments grouped by CIK (GOOG/GOOGL share one fetch); per CIK: submissions (SIC + newest 10-K/10-Q) -> skip when unchanged and no lag -> companyfacts -> extract -> one transaction upserting every Instrument row; a newer filing absent from companyfacts is stored as `pending_*`; 404 -> `no_data`; other failures keep the last figures and set `last_error`; 403 aborts the run. Scheduled as `fundamentals-refresh` weekdays 07:00 `America/New_York`, only when `SEC_FUNDAMENTALS_ENABLED`, `withoutOverlapping(90)`, `runInBackground()`.
- **Storage.** `company_fundamentals` (one row per Instrument, unique FK cascade; `cik`, `sic`, `is_financial`, `status` ok/partial/no_cik/no_data/error, period/balance-sheet/shares dates, latest and pending filing, `decimal(24,4)` inputs, `inputs` json provenance, `fetched_at`, `last_error`). Derived: skipped by `db:copy-sqlite-to-pgsql` and rebuilt by the command.
- **Read.** `CompanyFundamentalsService::payload()` returns `fundamentals-v1` (`FundamentalsMetrics::compute` on the stored inputs and the latest `daily_bars` close: P/E, EPS, market cap, revenue, growth, EBITDA, margin, net debt/EBITDA, ROIC, dividend yield, each `{value, period, reason}`); `context()` gives the AI provider the SEC metrics and, only with the rights flag, the price-derived ones. Operations: `docs/ai-company-card-operations.md`.

## Watchlist (Owned Resource)

- **Storage.** A watchlist is implicit (one per user): the `watchlist_items` pivot (`id`, `user_id`, `instrument_id`, `timestamps`, unique `(user_id, instrument_id)`) with cascade FKs to `users`/`instruments`. There is no `watchlists` table and no `WatchlistItem` model (the `instrument_universe` pivot precedent); ownership is `user_id` and removal is a hard delete (`docs/domain-model.md`: `active -> removed`, no soft delete). `User::watchlist()` is a `BelongsToMany(Instrument::class, 'watchlist_items')->withTimestamps()`; the explicit table name is required (Laravel would guess `instrument_user`).
- **Endpoints** (`app/Http/Controllers/WatchlistController.php`), all inside the existing `auth:sanctum` group so a guest gets **401**:
  - `GET /api/watchlist` -> `200 {items:[entry]}` ordered by `instruments.ticker` ASC.
  - `POST /api/watchlist` body `{ticker}` -> `201 {item}` (new) / `200 {item}` (already followed) / `422 {message, errors:{ticker}}` (missing, non-string or unknown ticker).
  - `DELETE /api/watchlist/{ticker}` -> `204` (removed) / `404 {message}` (unknown ticker or not in the caller's list).
  - `entry = {ticker, company, sector, exchange, active}` (the instrument-detail metadata field set). No endpoint accepts a `user_id`.
- **Ownership is the authorization model.** Every query runs through `$request->user()->watchlist()`. Another user's ticker simply does not match the scoped relation, so a cross-user read is an empty list and a cross-user delete is a `404` (no existence leak). An Admin has no special path here (`docs/user-and-access-model.md`).
- **Add/remove semantics.** The ticker is normalized (`trim` + `strtoupper`) before a `required|string|max:20` validation and an exact `instruments.ticker` lookup; `syncWithoutDetaching` makes the add idempotent (never a duplicate row, never a unique-index error). Remove uses `detach`, which reports `0` when the row was absent or someone else's, so it is not silently idempotent.
- **SPA.** `/portal` (`frontend/src/pages/PortalPage.tsx`, guarded by the component-level `frontend/src/auth/RequireAuth.tsx` -> `Navigate to /login replace`) aggregates the caller's Watchlist and Saved Screeners. It lists/removes Watchlist entries through `WatchlistTable`; the chart page (`/instruments/:ticker`) hosts the `WatchlistButton` "Seguir"/"Siguiendo" toggle. The chart stays anonymous and never redirects — the toggle reads auth only to offer a Visitor a sign-in **link**. `watchlistApi` in `frontend/src/lib/api.ts` (`list`/`add`/`remove`, CSRF before mutations) is the client; the API remains the enforcement point.

## Saved Screeners (Owned Resource)

- **Storage.** A real `saved_screeners` table (`id`, `user_id` FK `users` `cascadeOnDelete`, `name`, `filters` json, `timestamps`, unique `(user_id, name)`) with the `App\Models\SavedScreener` model. A Saved Screener has its own attributes (a name and a definition), unlike a follow relationship, so it is not a pivot; ownership is `user_id` and deletion is a hard delete (`docs/domain-model.md`: `draft -> saved -> deleted`, no soft delete). `user_id` is deliberately absent from `#[Fillable(['name','filters'])]` and rows are created through the scoped relation, so a client can never set ownership.
- **Endpoints** (`app/Http/Controllers/SavedScreenerController.php`), all inside the existing `auth:sanctum` group so a guest gets **401**:
  - `GET /api/screeners` -> `200 {screeners:[{id,name,filters}]}` ordered by `name` ASC then `id` ASC.
  - `POST /api/screeners` body `{name, filters}` -> `201 {screener}` / `422 {message, errors:{name|filters|filters.*}}`.
  - `DELETE /api/screeners/{screener}` -> `204` / `404 {message:"Screener not found."}`.
- **Ownership is the authorization model.** Every query runs through `$request->user()->savedScreeners()`; no endpoint accepts a `user_id`; another user's id simply does not match the scoped relation, so a cross-user read is an empty list and a cross-user delete is a `404` (no existence leak). An Admin has no special path here. `/screeners` does not collide with the public `/screener`.
- **Stored `filters` = the canonical seven-key API-param object (including `sort`).** `{signal, rsi_min, rsi_max, min_rvol, price_above_sma200, ma_cross, sort}` — the same vocabulary as `GET /api/screener`, so a stored definition is directly re-playable. `signal` is a JSON array of the 9 fixed type strings, deduped and stored in canonical order (never the comma form). Create validation whitelists the keys (`array:`), requires all seven (`present`) and mirrors the frozen screener API's value rules; an unknown key, an unknown signal type, an out-of-range value or an unknown `sort` is a `422` (never clamped or repaired). `name` is `required|string|max:60`, `trim`-ed, and unique per user (`422 errors.name`; two users may reuse a name; a case variant is a distinct name).
- **Apply = a URL round-trip.** A pure SPA helper (`frontend/src/lib/screenerFilters.ts`) serializes the live filters into the stored object (`serializeScreenerFilters`) and leniently deserializes a stored object back to a `Partial<ScreenerFilters>` (`deserializeScreenerFilters`, dropping unknown keys/values); the page applies it with the existing `patchScreenerFilters(prev, patch)` (`replace: true`). The fetch effect keyed on `screenerFiltersKey` then reissues `GET /api/screener` with exactly the stored params, so the Candidate list and the `Mostrando N de M` line are restored server-side. If the stored filters already equal the URL, the key is unchanged and no redundant request fires.
- **UI.** `frontend/src/components/screener/SavedScreenersPanel.tsx` is rendered on `/` below the filter panel. It is the only auth-aware affordance on the page (the page itself never calls `useAuth`): a Visitor sees a small sign-in **link** (`LOGIN_ROUTE`), never a redirect, so the Screener stays anonymous. A signed-in user sees a native `<details>` disclosure, closed by default, with the saved count in its summary. Opening it reveals the existing save row (name input + yellow "Guardar screener"), list (name + mono criteria summary + Aplicar/Eliminar), and loading/empty/error/saving/removing states; a `401` during a mutation is treated as session expiry -> `/login`. `savedScreenersApi` in `frontend/src/lib/api.ts` is the client (CSRF before mutations); the API remains the enforcement point.
- **Portal UI.** `frontend/src/components/portal/PortalSavedScreeners.tsx` adds a caller-scoped list/apply/delete section beside the existing Watchlist section without adding a portal API or cache. `Aplicar` deserializes the stored seven-key definition, creates a fresh `/screener` query with `patchScreenerFilters(new URLSearchParams(), patch)`, and lets the existing Screener effect fetch the ranked Candidate list. Delete uses `savedScreenersApi.remove()` then reloads only that session user's `savedScreenersApi.list()` response (a `404` is treated as already absent); `401` redirects to `/login`.

## Dependency Direction

- The SPA talks to Laravel over HTTP (JSON API); the auth endpoints above are the first ones. There is no code sharing between `frontend/` and the Laravel app.
- The Python engine is invoked by Laravel over HTTP (internal service), not directly by the SPA. The engine exposes `/health`, `GET /eod/{symbol}` (fetch + parse), `POST /indicators/compute` (indicator math) and `POST /signals/detect` (deterministic rules). Laravel talks to the engine through `App\Services\Engine\EngineClient` using the `ENGINE_URL` base URL.
