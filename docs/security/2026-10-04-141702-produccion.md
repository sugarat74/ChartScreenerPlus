# Informe de validación de seguridad web — Chartiko producción

## 1. Dictamen ejecutivo

- **Dictamen: NO APTO.** Dos fallos altos en los controles de permisos del release y confianza SSH en CI bloquean el despliegue mediante el flujo revisado.
- **Proyecto / entorno / release:** Chartiko, producción; Ubuntu 26.04 LTS, Nginx 1.28.3, PHP-FPM 8.5, Laravel + React SPA + FastAPI, SQLite. El enlace `current` apunta a `26fc5946af`, prefijo del commit local `26fc5946af99c541a6f0114318a3fc91e6520678`.
- **Fecha:** 2026-10-04 14:17 Europe/Madrid (UTC+02:00).
- **Objetivos:** `chartiko.com`, `www.chartiko.com`, VPS `51.222.158.148`, repositorio `C:\laragon\www\ChartScreenPlus` y flujo `deploy/` + GitHub Actions.
- **Modo y posición:** revisión mixta, desde Windows del operador y una sesión SSH de solo lectura como `deploy`; peticiones HTTP(S) públicas desde este equipo. No se usaron credenciales de la aplicación ni cuentas reales.
- **Bloqueos:** SEC-001 (el grupo del proceso web puede modificar el directorio que contiene `current` y áreas compartidas); SEC-002 (CI confía en una clave SSH obtenida sin verificación independiente).
- **Siguiente acción:** corregir SEC-001/002 y recuperar el permiso de `systemctl` limitado que espera `deploy.sh`; después revalidar permisos, CI y despliegue. Ver también el estado de sudo descrito en E-011/SEC-009.

Este dictamen cubre la evidencia observada en esta fecha; no certifica el sitio ni garantiza ausencia de vulnerabilidades. No se modificó la configuración de producción durante esta revisión. Las únicas escrituras fueron este informe y los artefactos de seguimiento del repositorio.

## 6. Hallazgos priorizados

### SEC-001 — El usuario web puede alterar releases y activación

- **Severidad / prioridad / bloqueo:** ALTA / P0 / bloquea aprobación.
- **Controles:** FILE-04, OPS-01.
- **Hecho:** el bootstrap asigna `deploy:www-data` y añade escritura de grupo de forma recursiva a `/var/www/alphapulse`; en producción los directorios `alphapulse`, `releases` y `shared` son `775 deploy:www-data`, mientras los servicios corren como `www-data` (E-006, E-014).
- **Impacto:** un proceso web/engine comprometido puede alterar el directorio padre del symlink `current`, intentar cambiar la release y reemplazar entradas compartidas. Es una vía de persistencia y manipulación de datos; no se afirma que haya ocurrido una intrusión.
- **Corrección:** hacer que solo `deploy`/root escriban el directorio de activación y releases; retirar escritura de `www-data` de `.env` y código. Dar escritura al servicio únicamente en los directorios concretos requeridos (SQLite, `storage`, `bootstrap/cache`) y revisar el límite de escritura del engine.
- **Responsable / prioridad:** operaciones, antes del próximo release.
- **Cierre:** `stat`/ACL de directorios y archivos; probar que `www-data` no puede crear/reemplazar `current`, cambiar código o sustituir `.env`, mientras Laravel/engine siguen escribiendo solo datos permitidos.
- **Rollback:** guardar modos/propietarios previos; restaurar solo permisos funcionales de datos si falla servicio, nunca volver a hacer escribible el padre de `current` por `www-data`.
- **Estado:** abierto.

### SEC-002 — CI no autentica la identidad SSH del VPS

- **Severidad / prioridad / bloqueo:** ALTA / P0 / bloquea publicación por GitHub Actions.
- **Control:** SUPPLY-02.
- **Hecho:** `.github/workflows/ci-deploy.yml` agrega la clave observada por `ssh-keyscan` al `known_hosts` del job sin compararla con una huella fijada por un canal independiente (E-014).
- **Impacto:** si se intercepta o redirige la conexión durante el job, un host impostor puede recibir el release o modificarlo. No se observó MITM ni exposición de claves privadas.
- **Corrección:** fijar `known_hosts`/huella verificada mediante consola del proveedor, mantener comprobación estricta y dar permisos mínimos al token de GitHub y al environment de producción.
- **Cierre:** CI conecta con el host legítimo fijado y rechaza una clave distinta en staging/prueba.
- **Rollback:** pausar despliegues y verificar cualquier rotación fuera de banda; no retirar la validación de host.
- **Estado:** abierto.

### SEC-003 — Instalador Composer se ejecuta como root sin verificación previa

- **Severidad / prioridad:** MEDIA / P1.
- **Control:** SUPPLY-02.
- **Hecho:** `deploy/setup-server.sh` descarga el instalador HTTPS y lo pasa directamente a `php` como root sin contrastar checksum/firma (E-014).
- **Impacto:** un compromiso de la cadena de entrega/TLS podría ejecutar código de instalación con privilegios máximos; no se afirma compromiso actual.
- **Corrección:** descargar el instalador a temporal, verificar su SHA-384/firma por el procedimiento oficial y fallar cerrado antes de ejecutarlo.
- **Responsable / cierre / rollback:** operaciones; probar que un instalador alterado se rechaza y conservar un binario verificado de recuperación. P1, antes del siguiente bootstrap.
- **Estado:** abierto.

### SEC-004 — Registro público sin rate limit

- **Severidad / prioridad:** MEDIA / P1.
- **Control:** AUTH-05.
- **Hecho:** `POST /api/register` no tiene middleware throttle mientras login sí limita intentos (E-014).
- **Impacto:** automatización que complete CSRF puede crear cuentas repetidamente y consumir CPU de hashing y almacenamiento. No se hizo carga ni alta masiva.
- **Corrección:** aplicar un limitador específico a registro, límites de cuerpo/contraseña y respuesta 429 documentada; probar con usuarios sintéticos.
- **Responsable / cierre / rollback:** backend, antes de abrir registro público; conservar un límite antiabuso al ajustar el umbral.
- **Estado:** abierto.

### SEC-005 — El engine acepta series de barras sin tamaño máximo

- **Severidad / prioridad:** MEDIA / P1.
- **Control:** APP-02.
- **Hecho:** los modelos de cálculo/detección declaran `bars: list[Bar]` sin máximo explícito. El servicio está en loopback y no se demostró acceso remoto.
- **Impacto:** una llamada local o una exposición futura accidental puede agotar memoria/CPU con listas grandes.
- **Corrección:** establecer máximo de barras conforme al histórico EOD soportado, límite de bytes por request y concurrencia/tiempo; mantener engine privado.
- **Responsable / cierre / rollback:** engine/backend antes de admitir payloads no confiables; probar aceptación del máximo y rechazo del exceso en entorno aislado.
- **Estado:** abierto.

### SEC-006 — Faltan cabeceras de defensa en la respuesta web

- **Severidad / prioridad:** BAJA / P2.
- **Controles:** HTTP-01, TLS-04.
- **Hecho:** no se observan CSP, protección de framing, `nosniff`, Referrer-Policy, Permissions-Policy o HSTS en la portada HTTPS (E-009).
- **Impacto:** falta defensa adicional frente a framing, carga de recursos inesperados y downgrade de primera visita. No demuestra XSS ni contenido mixto.
- **Corrección:** añadir `nosniff`, política anti-framing y Referrer-Policy; diseñar CSP desde el build real; activar HSTS tras validar todos los hosts. No usar `includeSubDomains`/preload sin inventariar subdominios.
- **Cierre / rollback:** comprobar GET de SPA, login y errores; retirar o afinar la directiva que rompa el producto, sin desactivar otras protecciones.
- **Estado:** abierto.

### SEC-007 — APP_URL de producción conserva HTTP y la IP

- **Severidad / prioridad:** BAJA / P2.
- **Control:** TLS-03.
- **Hecho:** el `.env` efectivo mantiene `APP_URL=http://51.222.158.148` aunque Nginx sirve Chartiko por HTTPS bajo `chartiko.com` y `www.chartiko.com` (E-005).
- **Impacto:** generación de URLs absolutas puede apuntar a la IP o a HTTP; no se observó un endpoint actual explotable ni una fuga de sesión.
- **Corrección:** alinear `APP_URL` con el host canónico HTTPS y regenerar la caché de configuración en un release controlado; conservar el nombre de cookie de sesión existente.
- **Cierre / rollback:** inspeccionar URLs generadas y repetir login/CSRF en staging; restaurar el valor previo si falla una integración y dejar HTTPS forzado en el proxy.
- **Estado:** abierto.

### SEC-008 — Rollback no revierte todos los componentes del release

- **Severidad / prioridad:** BAJA / P2.
- **Control:** OPS-05.
- **Hecho:** `deploy/deploy.sh` vuelve a la release anterior si falla el health check del engine, pero migraciones y venv compartidos ya pueden haber cambiado (E-014).
- **Impacto:** una migración incompatible o cambio de dependencia puede dejar la release anterior inutilizable aunque el enlace vuelva atrás.
- **Corrección:** documentar migraciones expand/contract y compatibilidad hacia atrás; versionar el entorno engine o declarar los pasos manuales de recuperación y backup.
- **Cierre / rollback:** simulacro en staging con fallo después de migración que restaure aplicación/datos/engine; no se ejecutó en producción.
- **Estado:** abierto.

### SEC-009 — Falta el permiso NOPASSWD limitado que usa el despliegue

- **Severidad / prioridad:** MEDIA / P1 operacional.
- **Control:** OPS-05.
- **Hecho:** la revisión confirmó que `/etc/sudoers.d/deploy` ya no está y `sudo -n -l` exige autenticación. `setup-server.sh` crea ese mismo archivo con permisos limitados para `systemctl`; `deploy.sh` invoca reinicios y recargas no interactivos (E-011, E-014).
- **Impacto:** el siguiente deploy automático puede cambiar `current` y fallar al intentar reiniciar servicios; el release y procesos activos pueden quedar desincronizados. No afecta las respuestas HTTP actuales.
- **Corrección:** restaurar solo la regla restringida ya definida en `deploy/setup-server.sh`, no la regla temporal `NOPASSWD: ALL`: `deploy ALL=(root) NOPASSWD: /bin/systemctl restart alphapulse-engine alphapulse-queue, /bin/systemctl reload php8.5-fpm, /bin/systemctl reload nginx`.
- **Responsable / prioridad:** operaciones, antes del siguiente deploy.
- **Cierre:** desde SSH comprobar `sudo -n -l` y ejecutar una validación no destructiva de sintaxis con `visudo -cf`; confirmar que no existe permiso NOPASSWD global. Probar un deploy en staging.
- **Rollback:** quitar solo la regla restringida si deja de usarse y adaptar el workflow/deploy a una vía administrativa explícita antes del siguiente release.
- **Estado:** abierto; pendiente de restauración desde consola root del proveedor.
